## Retained deliberately

### Historical calendar and Deadline code

The V2, V2.1, and Deadline families contain substantial old surface area, but they are not one
safe deletion unit:

- V5 still uses lunar/holiday logic originating in the V2.1 model family.
- Deadline storage and notification scheduling still participate in normal startup even though
  the current visible workbench is V5.
- Historical preview entry points remain useful for comparison while the current V5 worktree is
  still under active visual iteration.

Later cleanup should first extract the shared calendar primitives, prove that Deadline runtime
wiring is no longer needed, and then name exact files for user approval. Blindly deleting the
whole families would risk compile breaks, background behavior changes, or loss of comparison
evidence.

### Product evidence and handoffs

- `docs/product/approved/evidence/` is about 30 MB and contains runtime screenshots/recordings.
  It is historical acceptance evidence, not a build artifact.
- `docs/handoff/2026-08-29-new-window/` contains eight substantive handoff documents plus Finder
  metadata. It is currently untracked and should be reviewed for privacy before any commit.
- Seven ignored `.DS_Store` files total roughly 64 KB. They have no product value, but they were
  not removed because the user has not approved those exact targets and the space saving is
  immaterial.
- `.git/` is about 31 MB and is normal repository history, not a cleanup target.

## Remaining risks and recommended order

1. Finish and visually accept the current V5 interaction work already present in the dirty
   worktree; do not mix it with historical-code removal.
2. Always capture the full visible version identity in screenshots and bug reports. A release
   number alone no longer identifies a source preview.
3. Audit the normal-start Deadline wiring, then decide whether to keep it as a compatibility
   module or retire it.
4. Extract V5's shared lunar/holiday dependency before considering removal of old preview views.
5. Decide separately whether the untracked dated handoff package should be sanitized and
   committed, retained locally, or moved to an explicitly approved archive.
6. If desired, request a second cleanup by naming the exact `.DS_Store` or historical-code
   targets. No retained material should be deleted merely because it appears old.
