# Desktop Sentry 日历与桌面待办看板

- Status: DRAFT
- Owner: product discussion
- Created: 2026-08-20
- Updated: 2026-08-21
- Approval: pending
- Approved specification: `docs/product/approved/SPEC-001-DEADLINE-REMINDERS.md`

## 用户问题与期望结果

Desktop Sentry 当前左键直接复制常驻提示词，右键打开原生菜单。用户希望在不把应用做重的前提下，增加一个面向 deadline / 倒数日的提醒工具：能看到距离某件事还有多久，未来可查看时间线；理想状态还包括把选中的提醒缩成一个可拖动的小框并固定显示。

参考界面的可借鉴部分是：月历与今日/近期事项并排、当天高亮、日期上的节日标记、右侧待办列表，以及可固定显示。它是视觉和交互参考，不是要求复制完整日历软件的全部功能。

## 当前已知事实

- 当前 `TaskItem` 没有计划日期、截止日期、全天/定时或提醒字段，只有标题、完成状态、创建时间、优先级、标签、Skill 关联和软删除时间。
- 用户已明确：现有待办没有具体执行日期，不要求迁移或补日期。deadline / 倒数日应先作为独立候选模块，是否与普通待办关联以后再讨论。
- 用户已明确：同一个被关注的 deadline 必须同时在菜单栏持续显示剩余天数，并在到达指定日期/时间时触发带声音的 macOS 弹窗通知。
- 用户已确认菜单栏空间不足时 Deadline 剩余天数优先，允许缩短常驻提示词。
- 用户认可参考截图的简约、轻盈设计语言和主要操作逻辑；参考图用于提取层级、布局与反馈原则，不作为逐像素复制或产品指令。
- 用户已确认页面展示方案：使用一个原生菜单栏项目，文字区单击复制，右侧日历图标单击打开中等尺寸、可拖动的独立双栏 Deadline 面板；首版不做钉到桌面。
- 用户已确认：可以创建多个 Deadline，每项可独立安排弹窗和声音；菜单栏一次只显示一个用户选中的重点 Deadline。切换重点项不得取消或改变其他 Deadline 已安排的通知。
- 用户已确认时间规则：目标日期必填；只显示倒数时可以不填具体时间；开启弹窗和声音时必须明确选择通知时间；应用不得擅自使用午夜、早上 9 点或其他默认提醒时间。
- 用户已确认首版提醒频率：每个 Deadline 到点只弹窗并响铃一次；首版不自动重复、不连续催促、不提供稍后提醒。未处理的重点 Deadline 在菜单栏持续显示“今天”或“已到期 N 天”，直到完成或归档。
- 用户已确认重点项接续规则：当前菜单栏重点 Deadline 完成或归档后，自动切换到目标时间最近的下一项；如果没有其他进行中项目，就隐藏 Deadline 倒数。用户仍可随时手动选择其他重点项。
- 现有数据保存在本地 JSON 中；新增独立 deadline 数据仍需采用兼容默认值，确保旧数据无损加载。
- 左键复制是当前稳定核心行为，右键原生菜单是主要管理入口。
- 当前菜单栏标题已经可能包含常驻提示词、自定义文字和普通待办计数，并允许 10–25 字的提示词长度设置；加入 deadline 后必须定义信息优先级，避免标题无限增长。
- 项目已有 SwiftUI + `NSPanel` 的窗口基础，并已有跨 Space 显示的面板行为；但“固定在桌面背景层”和“始终浮在其他应用上方”是两种不同体验。
- macOS 已支持把小组件放到桌面和通知中心，也可以点击菜单栏日期时间打开通知中心；但这不等同于 Windows 式的完整月历快捷面板。
- Apple EventKit 可以读取和修改系统日历、提醒事项，但读取需要完整访问权限；用户拒绝授权时必须正常降级。提醒事项与日历是两类独立授权。

## 关键未知与产品分叉

### 1. “钉在桌面”到底指什么

- 桌面层：像系统桌面小组件，通常位于普通应用窗口后面。
- 置顶层：像浮动便签，切换应用后仍压在窗口上方。
- 普通常驻窗口：记住位置和尺寸，但会被其他窗口遮挡。

三者的打扰程度、Mission Control / Space / Stage Manager 行为和实现维护成本不同，不能用一个“固定”按钮含糊处理。

### 2. deadline 与普通待办的关系

普通待办回答“我要做什么”，deadline 回答“距离某个时间点还有多久”。用户当前不希望给旧待办补日期，因此第一版不应强迫两者共用一个模型。deadline 可以独立创建，至少包含标题、目标日期/时间和完成/归档状态；以后如证明有价值，再增加与普通待办的可选关联。

首版时间字段规则已经确认：标题与目标日期必填；通知开关关闭时目标时间可以为空；开启通知时必须由用户明确选择目标时间。界面不得悄悄补入默认时间，保存前应直接说明缺少通知时间。

### 3. 菜单栏与系统通知的联动

- 用户从多个 deadline 中选择一个“菜单栏关注项”；菜单栏只显示这一项的剩余天数，避免同时展示多个倒数。
- 每个 deadline 的通知状态彼此独立；没有显示在菜单栏中的 deadline 仍应按各自设定正常通知。
- 候选紧凑格式为 `⏳3天`、`今天`、`已到期1天`；完整标题在右键菜单或 deadline 界面查看。
- 剩余天数在创建、编辑、完成、切换关注项和跨过午夜时更新，不做每秒倒数。
- 通知绑定同一个 deadline：创建或修改目标时间时安排/重排，完成、归档或删除时取消尚未触发的通知。
- 首次主动开启某个 deadline 的提醒时，再向用户请求通知权限；不在应用首次启动时突然索取权限。
- 开启通知但尚未选择具体时间时不能安排通知，界面应就地提示用户选择时间；不得静默采用默认时间。
- 第一版使用 macOS 标准通知弹窗和系统声音。专属铃声、连续响铃、强制突破专注模式不属于默认能力。
- 每个 deadline 的首版通知只触发一次；点击通知打开对应 deadline。通知触发后不自动创建下一次提醒，也不提供“稍后提醒”。
- 一次通知未被处理时，不用后台循环催促；若该项是菜单栏关注项，菜单栏继续显示“今天”或“已到期 N 天”，直到用户完成或归档。
- 菜单栏关注项完成或归档后，自动选择目标时间最近的下一项；没有其他进行中 deadline 时清空关注项并隐藏倒数。自动接续不得修改其他项目的通知状态。
- 用户拒绝通知权限或系统关闭声音时，菜单栏倒数仍继续工作，并清楚显示通知未启用。

### 4. 单个菜单栏项目内的两个点击区

已确认交互：菜单栏左侧文字区域单击仍复制当前常驻提示词；右侧增加一个可见的日历/Deadline 图标，单击图标打开 Deadline 页面；右键点击任意区域仍打开现有原生菜单。

当前项目使用一个标准 `NSStatusItem` / `NSStatusBarButton`。AppKit 允许标准按钮同时显示标题和图像，并把图像放在标题右侧。候选实现是在同一个原生按钮内保留固定宽度的右侧图标点击区，按左键事件在按钮中的横向位置分发动作。

建议约束：

- 使用一个状态栏项目，保证文字与图标始终相邻，不创建两个可被用户拖散的独立状态栏项目。
- 右侧图标视觉尺寸保持克制，但实际点击区约 22pt；文字与图标之间保留清楚间距或轻分隔。
- 按下时立即提供系统高亮反馈；弹出的页面从图标附近出现，保持触发点与结果的空间联系。
- 右键菜单保留“打开 Deadline / 倒数日…”作为辅助功能与故障兜底；该图标不能成为唯一入口。
- 需要为 VoiceOver、键盘路径、菜单栏空间不足、多显示器、刘海屏和 macOS 26 的状态栏复制视图做真实验证。
- 不采用已经被 AppKit 弃用的 `NSStatusItem.view` 自绘方案。若同一标准按钮内的坐标分区在真实系统上不稳定，先退回“文字单击复制 + 右键菜单打开 Deadline”，不得静默改成两个容易分离的状态栏项目。

该方案技术上可行，但正式批准前应先做最小交互原型，在真实菜单栏验证命中区域、系统高亮、右键菜单和辅助入口，而不是只凭静态图判断。

### 5. 节假日数据从哪里来

- 只显示公历日期：无需外部数据，最稳定。
- 显示农历和传统节日：可本地计算或随应用携带数据，但节气与规则需要专门验证。
- 显示中国法定放假及调休：安排逐年发布，需要可靠更新来源；静态内置数据会过期。
- 读取用户系统日历中的节假日日历：需要日历读取权限，并取决于用户自己的日历配置。

“传统节日”和“法定放假/调休”不是同一份数据，不能混为一谈。

### 6. 是否同步系统日历与提醒事项

如果 Desktop Sentry 只显示自己的待办，功能可以完全本地、无需新权限。若要读写 Apple Calendar 或 Reminders，则必须做成可选模块，解释权限用途，处理拒绝授权、外部修改、重复项和同步冲突，且关闭模块不能影响本地待办。

## 方案比较

### 方案 A：独立 deadline / 倒数日工具（建议第一阶段）

- 保留现有左键复制。
- 在右键菜单增加明确的“Deadline / 倒数日…”入口；可另配快捷键，但不依赖隐藏手势。
- 打开一个紧凑界面，展示目标日期、剩余天数和按时间排序的近期 deadline；月历视图可以作为辅助，而不是产品中心。
- deadline 独立存储，不迁移、不自动修改现有待办。
- 菜单栏显示用户选择的一个 deadline 的剩余天数；到达目标时间时安排 macOS 弹窗和声音提醒。
- 首阶段不访问系统日历、不联网、不做重复任务。本地通知是已确认范围，但它不要求日历读取权限。
- 可先提供普通窗口；“固定显示”作为独立可逆阶段验证。

优点：直接解决“别忘记重要日期”和未来时间线的问题，隐私与维护成本最低，也不污染普通待办。缺点：第一阶段不是完整日历，不会自动出现系统日程和法定调休。

### 方案 B：方案 A + 可拖动的固定提醒小框

- 用户从 deadline 列表选中一项并点击固定后，桌面出现一个显示名称、目标日期和剩余时间的小框。
- 小框可拖动，并有明确的关闭/取消固定入口；第一版可只允许固定一项，以验证价值和打扰程度。
- 提供明确的显示模式，例如“普通窗口”或“置顶提醒”。
- 记住位置、尺寸和显示模式，提供随时退出固定状态的明显入口。
- 必须分别验证多显示器、Space、全屏应用、Stage Manager、显示器拔插、睡眠唤醒和开机登录。

优点：接近参考软件的提醒价值。缺点：窗口层级很容易变成遮挡、抢焦点或“怎么都关不掉”的打扰源；不能只凭截图判断体验。

### 方案 C：完整日历中心

- 加入 Apple Calendar / Reminders、节假日/农历、倒数日、重复任务、通知和更丰富的桌面固定能力。

优点：功能完整。缺点：授权、同步、数据冲突、年度数据维护、签名与发布验证都会显著增加，容易把 Desktop Sentry 变成第二个日历软件，偏离轻量核心。目前不建议作为一个整体实施。

### 暂时不做

继续使用 macOS 通知中心的系统日历/提醒事项小组件，Desktop Sentry 只保留现有待办。这没有开发和迁移风险，但 Desktop Sentry 不会形成自己的 deadline 时间线或固定提醒小框。

## 当前建议

先验证方案 A，并把方案 B 的“固定小框”作为后续独立阶段。界面可以借鉴参考图的 deadline 列表、倒数天数和固定操作，但不复制 24 节气、自定义节日、完整日程和主题系统。

左键文字区域继续复制。右侧可见日历图标打开 Deadline / 倒数日页面，右键菜单同时保留显式入口；现有左键核心行为不被替换。

## 已确认的页面方向与候选设计细节

已确认使用中等尺寸、可拖动的独立双栏 Deadline 面板，首版不做钉到桌面。页面借鉴参考截图的总体气质，但以 Desktop Sentry 的功能边界重新组织：

- 使用系统字体、SF Symbols、原生玻璃材质、柔和圆角与克制阴影，适配浅色/深色、增强对比度和减少透明度设置。
- 主界面保持“左侧月份 / 时间定位，右侧 Deadline 列表”的清楚双栏；当前日期和被选中的 Deadline 使用有限的系统强调色，其余内容保持中性。
- 信息层级优先展示名称、目标日期和剩余天数；节气、主题、自定义分类等未批准能力不占首版界面。
- 图标点击后打开独立 Deadline 面板，而不是跳进庞大的偏好设置页。面板首次从菜单栏图标附近出现；若尺寸较大无法合理锚定，则在当前屏幕居中并记住用户移动后的位置。
- 面板可拖动、可关闭，打开与关闭路径一致，动画克制且可中断；尊重“减少动态效果”和“减少透明度”。
- “钉到桌面”按钮可以保留视觉位置但在功能未批准前不得出现不可用的假按钮；首版若不实现固定模式，就不展示该控件。
- 参考产品的布局可用于验证信息密度，但不逐像素复制其专有图标、文案、节日数据或完整功能组合。

## 初步资源占用估算

2026-08-20 对当前已安装 `1.1.0 build 11` 的只读测量：应用包约 2.4 MB；运行进程 RSS 约 28 MB、物理内存 footprint 约 104 MB、采样时 CPU 为 0.0%。RSS 与 footprint 是不同统计口径，不能直接相加。

以下是尚未做原型前的增量估算，不是验收结果：

- 独立 deadline 数据与紧凑界面：安装体积约增加 0.2–1 MB；界面打开时约增加 5–15 MB 内存。
- macOS 本地通知：安装体积通常只增加少量代码，预计低于 0.5 MB；运行增量约 0–2 MB。通知提交后由系统跟踪触发时间，不需要应用每秒轮询。
- EventKit 读取系统日历：框架由 macOS 提供，不会把整套日历框架复制进应用包；安装体积预计增加低于 0.5 MB。若只按可见月份或未来 90 天读取并只缓存摘要，运行增量可控制在约 3–15 MB；读取多年历史或保留大量 EventKit 对象会明显升高。
- 三者同时加入后，应用包大概率仍在约 3–5 MB 量级；相关窗口打开时，相对当前进程增加约 10–30 MB 内存是合理预算。精确值只能由真实原型、固定测试数据和 Instruments / `footprint` 测量确认。

资源风险主要来自错误实现：每秒刷新倒数、后台频繁轮询日历、一次读取全部历史、保存大量系统事件对象。正确做法是按窗口范围读取、监听系统变更、缓存轻量摘要，并按“天”或必要的“分钟”刷新。

## 风险与失败行为

- 数据迁移：新增 deadline 集合必须有兼容默认值，旧待办不能被自动指定日期、迁移或丢失。
- 产品臃肿：月历、系统日历同步、提醒、节假日数据、桌面固定必须拆成独立边界。
- 隐私：未主动启用系统集成时不请求日历或提醒事项权限；拒绝授权后本地月历仍可用。
- 提醒可靠性：应用可以请求弹窗与声音，但专注模式、勿扰模式和用户的系统通知设置具有最终控制权；产品不得承诺绕过系统设置强制发声。
- macOS 行为：固定窗口不得抢焦点、遮挡全屏工作或无法退出；多 Space 行为必须明确。
- 数据正确性：不得把静态节日数据称作当年法定放假安排，也不得在未验证时声称农历/节气完全准确。
- 视觉维护：不应继续把大量新界面堆入现有较大的 `SettingsView.swift`；若实施，需要清晰的新界面边界。

## 暂定非目标

- 克隆参考软件或做一套完整 Calendar 替代品。
- 首阶段读取或修改 Apple Calendar / Reminders。
- 首阶段提供重复任务、位置提醒、连续响铃、强制突破专注模式或自动化。
- 首阶段提供通知重复、自动催促或稍后提醒。
- 首阶段在线更新节假日、24 节气或主题皮肤。
- 未经单独讨论，改变现有左键复制行为。
- 未经用户明确操作，自动把 Desktop Sentry 待办写入系统日历。

## 候选验收标准（尚未批准）

- 用户可通过可发现的入口打开 deadline / 倒数日界面，而不破坏现有左键复制和右键菜单行为。
- 用户能按目标时间查看近期 deadline；若保留月历辅助视图，它应能切换月份、回到今天并标出存在 deadline 的日期。
- 用户可独立创建、编辑、完成或归档 deadline，并看到剩余天数或时间线排序。
- 创建 deadline 时标题和目标日期必填；具体时间在通知关闭时可省略，在通知开启时必填且必须由用户明确选择。
- 用户可选择一个 deadline 作为菜单栏关注项；菜单栏在不改变左键复制行为的前提下显示其剩余天数。
- 用户可为多个 deadline 分别开启、关闭和安排通知；切换菜单栏关注项后，其他 deadline 的待触发通知保持不变。
- 菜单栏关注项完成或归档后自动显示目标时间最近的下一项；没有下一项时隐藏倒数，且其他项目的通知安排保持不变。
- 菜单栏文字区单击复制常驻提示词；右侧日历图标单击打开 Deadline 页面；右键任意区域继续打开现有菜单。
- 日历图标拥有足够的实际点击区和清楚的按下反馈，并能通过右键菜单中的备用命令完成同一操作。
- 到达任一已开启通知的 deadline 日期/时间时，macOS 在获得授权的情况下显示弹窗并播放系统通知声音。
- 每个 deadline 到点只通知一次；点击通知打开对应项目，未处理的菜单栏关注项继续显示已到期状态。
- 编辑目标时间后旧通知被取消并重新安排；完成、归档或删除后不再出现过期通知。
- 通知权限被拒绝或随后关闭时，deadline 与菜单栏倒数仍可正常使用，并向用户显示真实的通知状态。
- 普通待办不要求填写日期，旧待办不被迁移或修改。
- 老版本数据首次加载后内容、完成状态、优先级、标签和 Skill 关联保持不变。
- 本地月历在没有网络、未授予日历权限或权限被拒绝时仍正常工作。
- 窗口关闭、重新打开、切换 Space 以及多显示器使用时没有抢焦点或遗失窗口。
- 若后续加入固定模式，必须有明显的取消固定入口，并通过人眼验证其在普通窗口、全屏和 Stage Manager 下的行为。

## 需要用户决定的一项关键问题

已确认“菜单栏倒数 + 到时弹窗和声音”必须同时存在，并确认空间不足时优先保证 Deadline 剩余天数、缩短常驻提示词。

页面展示已确认为：点击右侧日历图标后打开中等尺寸、可拖动的独立双栏 Deadline 面板；首版不做固定桌面小框，也不同时维护图标下方紧凑浮层。如果以后需求发生变化，再作为独立候选重新讨论。
